# commit

변경사항을 분석해 논리적 단위로 나누고, 한국어 커밋 메시지로 커밋한다.

## 절차

### 1. 변경사항 분석

저장소인지 먼저 확인하고(`git rev-parse --is-inside-work-tree`), 아래를 실행한다.

```bash
git status --short
git diff            # 아직 stage하지 않은 변경
git diff --staged   # 이미 stage된 변경
git log --oneline -10   # 기존 메시지 스타일 참고
```

- 변경이 없으면 그 사실을 알리고 끝낸다.
- 새 파일(untracked)도 내용을 읽어 목적을 파악한다.
- `.env`, 키·토큰, `node_modules`, 빌드 산출물(`dist`) 등은 커밋 대상에서 제외하고 사용자에게 알린다.

### 2. 논리적 단위로 분류

- 하나의 커밋은 하나의 목적만 담는다. 기능 추가, 버그 수정, 리팩터링, 설정 변경이 섞여 있으면 나눈다.
- 같은 파일 안에서 목적이 다른 변경이 섞여 있어도 나눌 수 있다(`git add -p`는 대화형이라 쓸 수 없으므로, 나누기 어려우면 하나로 묶고 이유를 설명한다).
- 의존 순서를 고려해 커밋 순서를 정한다.

### 3. 커밋 메시지 작성

형식:

```
<type>: <요약>

<본문(선택)>
```

| type | 용도 |
|------|------|
| feat | 새 기능 |
| fix | 버그 수정 |
| refactor | 동작 변화 없는 구조 개선 |
| chore | 설정, 의존성, 빌드, 잡무 |

저장소의 기존 로그가 `docs`, `style`, `test` 등 다른 type을 쓰고 있으면 그것을 따른다.

규칙:
- 요약은 한국어, 50자 안팎, 마침표 없이 쓴다. 예: `feat: 프롬프트 예시 선택 기능 추가`
- "무엇을"보다 "왜"가 드러나게 쓴다. 본문은 요약만으로 부족할 때만 쓴다.
- 요약 한 줄에 서로 다른 목적을 `및`으로 이어 붙이지 않는다. 그럴 땐 커밋을 나눈다.
- 메시지 끝에 현재 환경이 지정한 공동 작성자(Co-Authored-By) 줄이 있으면 빈 줄 뒤에 붙인다.

### 4. 사용자 승인

커밋 전에 아래를 보여주고 승인을 받는다(AskUserQuestion 사용).

- 커밋별로 포함할 파일 목록
- 커밋 메시지 전문
- 제외한 파일과 그 이유

사용자가 수정을 요청하면 반영해 다시 확인한다. 승인 전에는 `git add`/`git commit`을 실행하지 않는다.

### 5. 커밋 실행

승인된 커밋을 순서대로 실행한다.

```bash
git add <파일...>        # 파일을 명시한다. git add -A / . 는 쓰지 않는다.
git commit -m "<메시지>"
```

- 여러 줄 메시지는 heredoc으로 전달한다.
- pre-commit hook이 실패하면 원인을 고쳐 새 커밋으로 만든다. `--no-verify`, `--amend`, `push`는 사용자가 요청할 때만 한다.
- 마지막에 `git log --oneline -<n>`과 `git status --short`로 결과를 확인하고 요약해서 알린다.

## 하지 말 것

- 승인 없이 커밋하기
- 모든 변경을 한 커밋에 몰아넣기
- 비밀 정보가 담긴 파일을 stage하기
- 사용자가 요청하지 않은 push, force 옵션, 히스토리 재작성
